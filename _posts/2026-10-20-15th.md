# 🔍 들어가며

Claude Code와 Codex를 개발에 활용하고 있습니다. 기존 코드의 흐름을 파악하거나 기능을 구현하고, 테스트와 문서를 정리할 때 함께합니다.

제가 다루는 서비스에는 화면만 보고는 알기 어려운 조건이 많습니다. 같은 데이터를 여러 화면이 사용하고, 요청이 진행되는 동안 사용자가 다른 대상을 선택하기도 합니다. API 요청은 성공했지만 후속 조회는 실패할 수 있고, 웹에서 구현한 동작을 앱에도 전달해야 할 때가 있습니다.

AI가 이 맥락을 모르면 요청한 기능은 동작하더라도 기존에 지켜야 할 조건이 달라질 수 있습니다. 그래서 저는 작업에 필요한 정보와 변경의 경계, 완료를 판단할 근거를 함께 관리합니다.

복지몰 대중교통을 개발하며 다룬 사례들이 이 방식을 잘 보여줍니다.

![AI에게 맡기기 전에 맥락, 경계, 완료 근거를 정한다](/images/blogImg/ai-01-context.png)

# 🔍 반복되는 설명은 프로젝트에 남긴다

프로젝트의 상태 관리 방식, 공통 컴포넌트, 오류 처리 규칙을 매번 대화로 설명하기는 어렵습니다. 저는 CLAUDE.md와 AGENTS.md, 기능별 정책 문서를 작업의 기준으로 사용합니다.

실제 지침에는 다음과 같은 내용이 있습니다.

> - UI·입력·검증을 새로 만들기 전에 기존 공통 컴포넌트와 공유 패키지를 먼저 검색한다.
> - 기존 컴포넌트·훅·유틸리티를 우선 재사용한다.
> - 문서화된 동작이 바뀌면 관련 문서도 같은 작업에서 갱신한다.

AI에는 구현 전에 루트와 해당 앱의 지침을 읽고, 작업과 관련된 문서·기존 코드·테스트를 확인하도록 합니다. 요청마다 모든 내용을 붙여 넣기보다, 프로젝트 안에서 필요한 맥락을 찾는 순서를 정해 둡니다.

결과도 같은 기준으로 검토합니다. 새 입력 화면에 기존 formatter와 오류 컴포넌트가 연결됐는지, 정책 변경이 문서에 반영됐는지 살펴봅니다.

문서에는 현재 동작과 검토 중인 제안도 구분해 둡니다. 과거의 가설이 다음 작업에서 확정된 정책처럼 사용되지 않게 하기 위해서입니다.

![매번 말하는 대신, 맥락을 찾는 순서를 남겼다](/images/blogImg/ai-02-repeat.png)

# 🔍 기능 요청에는 유지해야 할 조건을 함께 넣는다

"새로고침을 수정해 줘"라는 말에도 여러 판단이 숨어 있습니다.

대중교통의 전체 경로 새로고침은 경로와 시간표를 다시 확인합니다. 자동 갱신은 실시간 도착정보를 업데이트합니다. 특정 구간의 조회 실패를 재시도할 때는 다른 구간의 정상 결과까지 초기화할 필요가 없습니다.

프로젝트 정책을 바탕으로 요청을 재구성하면 다음과 같습니다.

> **처음 요청**: 새로고침 동작을 확인하고 수정해 줘.
>
> **구체화한 조건**: 전체 새로고침·자동 갱신·구간별 재조회를 구분한다. 자동 갱신에서는 시간표 세션을 유지하고, 구간별 재조회에서는 다른 구간의 성공 결과와 선택 상태를 유지한다. 관련 코드와 테스트를 함께 확인한다.

저는 무엇을 다시 계산할지와 어떤 상태를 유지할지 구분하고, AI에는 해당 조건이 구현된 위치를 조사하고 수정하도록 맡깁니다. 결과를 볼 때도 데이터가 새로 들어오는지뿐 아니라 사용자의 선택이 의도대로 남아 있는지 살펴봅니다.

![바꿀 것과 함께 유지할 것을 요청에 넣는다](/images/blogImg/ai-03-keep-conditions.png)

# 🔍 그럴듯한 추정이 제품의 사실이 되지 않도록 한다

대중교통 알림에서는 '일정 시간 관측되지 않으면 지나간 것으로 본다'는 규칙을 제거한 사례가 있었습니다. 외부 API에 문제가 생기면 아직 오지 않은 버스를 탑승한 것으로 처리할 수 있었기 때문입니다. ([대중교통 알림 상태 설계 회고](/14th/))

여기서 구분해야 했던 것은 관측되지 않았다는 사실과 실제로 지나갔다는 판단이었습니다.

이 사례는 AI와 작업할 때도 중요한 기준이 됩니다. 데이터가 없을 때 자연스러워 보이는 대체 동작을 만들 수는 있지만, 그 동작을 뒷받침할 근거가 있는지 먼저 봐야 합니다.

프로젝트 지침에도 코드·API·문서에서 확인되지 않은 값을 추측하지 않도록 명시합니다. 응답 누락을 실제 도착으로 바꾸거나, 조회 실패를 정상적인 빈 결과로 취급하거나, 시간표상 예상 위치를 실시간 관측처럼 표시하지 않도록 합니다.

정보가 부족하면 부족한 상태를 표현하고, 실제 단계가 바뀌었다고 판단할 조건은 별도로 둡니다. AI가 제안한 처리도 API 계약과 제품 정책에 비춰 검토합니다.

![그럴듯한 추정이 제품의 사실이 되지 않게](/images/blogImg/ai-04-guess-vs-fact.png)

# 🔍 최적화할 때는 데이터의 사용 조건부터 본다

버스 노선 캐시를 '저장 후 24시간'에서 '다음 한국시간 오전 4시' 만료로 바꾼 사례도 있습니다. ([버스와 지하철, 어디까지 실시간으로 조회해야 할까?](/13th/))

두 방식은 같은 하루 단위 캐시처럼 보이지만 동작이 다릅니다. 24시간 방식에서는 데이터를 저장한 시각에 따라 만료 시점이 달라집니다. 정해진 경계를 사용하면 그 시각 이후의 조회에서 새 데이터를 확인하도록 정책을 맞출 수 있습니다. 이 경계는 프론트엔드 정책이며, 원천 API가 그 시각에 갱신된다는 의미는 아닙니다.

이런 차이 때문에 "API 호출을 줄여 달라"는 요청만으로 최적화 방향을 결정하지 않습니다. 어떤 데이터를 재사용할 수 있고 언제 새로 확인해야 하는지부터 정리합니다.

현재 구현에서도 버스 노선 구조와 차량 위치는 별도로 조회합니다. 공통 요청 캐시는 진행 중인 동일 요청을 공유하고, 무효화 이전에 시작한 응답이 새 캐시를 덮지 않도록 합니다.

개선 결과를 설명할 때도 구현과 실측을 구분합니다. 요청 공유와 만료 처리를 확인했다는 사실만으로 운영 호출량이 몇 퍼센트 줄었다고 말하지는 않습니다.

# 🔍 응답이 도착했을 때도 유효한 결과인지 묻는다

버스 차량을 교체하는 중에 이전 알림의 응답이 도착해 알림이 취소될 수 있는 상황을 회귀 테스트로 다뤘습니다. ([대중교통 알림 상태 설계 회고](/14th/))

교체 전 알림의 조회가 늦게 끝나면 이전 대상에 대한 '알림 없음' 응답을 받을 수 있습니다. 이를 현재 알림에 적용하면 새로 선택한 대상까지 영향을 받습니다. 현재 구현에서는 교체 중 이전 알림의 조회 결과 적용을 막고, 연결된 후속 처리에도 유효성 확인을 전달합니다.

이런 비동기 코드를 볼 때 사용하는 질문이 있습니다.

> 요청을 시작했을 때와 응답을 받았을 때 상황이 달라져도, 이 결과를 적용해도 될까?

화면 이동, 대상 변경, 계정 변경에도 같은 질문을 적용합니다. 이전 계정에서 시작한 작업이 완료됐다고 새 계정의 작업 잠금을 해제해서는 안 됩니다.

AI에 조사와 구현을 맡길 때도 성공·실패 외에 이런 상황을 확인 범위에 포함합니다.

![응답이 도착했을 때도 유효한 결과인지 묻는다](/images/blogImg/ai-05-response-validity.png)

# 🔍 완료 보고는 네 가지로 나누어 읽는다

AI가 작업을 마쳤다고 보고하면 다음 내용을 구분해서 봅니다.

| 구분 | 확인하는 내용 |
| --- | --- |
| 코드 확인 | 어떤 조건과 처리 흐름이 구현되어 있는가 |
| 자동 검증 | 어떤 상황을 재현했고 무엇을 확인했는가 |
| 실제 환경 검증 | 브라우저·기기에서 어디까지 확인했는가 |
| 미확인 사항 | 환경이나 외부 시스템 때문에 무엇이 남았는가 |

프로젝트 지침에도 자동 테스트와 실제 브라우저·기기 검증을 구분하고, 미적용·미검증 항목을 별도로 보고하도록 둡니다. 완료 보고에서 실행한 검증과 남은 확인 사항을 읽을 수 있게 하기 위해서입니다.

실제 버스 알림 폴링 테스트에는 조회 주기가 10초인 상태에서 응답을 60초 지연하는 시나리오가 있습니다. 그동안 진행 중 요청이 하나만 유지되고, 완료 후 다음 조회가 재개되는지 확인합니다.

이 테스트는 느린 응답에서 요청이 중첩되지 않는다는 근거가 됩니다. 실제 공급자의 데이터 정확성이나 모든 브라우저 동작까지 증명하지는 않습니다.

테스트 개수보다 어떤 조건을 확인했는지 읽고, 확인하지 못한 부분은 후속 작업으로 남깁니다.

![완료 보고는 네 가지로 나눠 읽는다](/images/blogImg/ai-06-done-report.png)

# 🔍 한 번의 판단을 다음 작업에 연결한다

작업 중 결정한 정책이 대화에만 남으면 다음에 다시 설명해야 합니다.

반복되는 규칙은 프로젝트 지침에, 기능의 동작 조건은 정책 문서에, 다시 발생하면 안 되는 문제는 테스트에 남깁니다. 웹과 앱의 적용 상태가 다르면 인수인계 문서에서 구분합니다. 복지몰 수정이 끝났다는 이유로 RN까지 적용됐다고 기록하지 않습니다.

AI와 협업하면서 제가 집중하는 역할도 분명해지고 있습니다. 해결할 문제를 정하고, 유지할 동작을 구분하고, 결과를 확인하고, 그 판단을 다음 작업에 남기는 일입니다.

설명이 부족해 다시 요청할 때도 있고, 조사 범위나 수정 방향을 조정할 때도 있습니다. 그때마다 처음의 목적과 현재 결과를 다시 맞춥니다.

앞으로는 이 방식이 반복 설명과 재작업에 어떤 차이를 만드는지도 기록하려고 합니다. 제가 어떤 기준으로 결정했고 그 결과 무엇이 달라졌는지, 더 구체적인 근거로 설명하고 싶습니다.
