# 🔍 들어가며

복지몰 서비스에 버스·지하철 승하차 알림 기능을 만들었습니다. 사용자가 탈 열차나 버스를 고르면 "곧 도착", "도착", "탑승", "이용 완료" 순서로 진행 상황을 보여주고, 내릴 때가 되면 알려주는 기능입니다.

기능 자체는 금방 동작했습니다. 그런데 QA에서 이상한 화면이 계속 나왔습니다.

- "도착"이라고 표시됐다가 몇 초 뒤 다시 "곧 도착"으로 돌아감
- "탑승"과 "도착"이 번갈아 표시됨
- 열차를 바꾸는 중에 알림이 갑자기 종료됨
- 새로고침하면 진행 상황이 처음 단계로 돌아감

하나씩 보면 서로 다른 버그 같았습니다. 하지만 원인은 하나였습니다. 같은 상태를 바꾸는 주체가 너무 많았고, 그 사이에 규칙이 없었습니다.

---

# 🔍 1. 상태를 바꾸는 주체가 너무 많았다

알림 하나의 상태를 바꾸는 주체를 정리해 보니 다섯 곳이었습니다.

| 주체 | 특징 |
| --- | --- |
| 서버 알림 판정 | 서버가 열차를 관측해 단계를 갱신함 |
| 화면의 실시간 관측 | 주기적으로 받은 도착 정보. 누락되거나 순서가 뒤바뀌어 도착하기도 함 |
| 사용자 조작 | 등록, 열차 변경, 해제, 다른 알림으로 교체 |
| 자동 종료 | 시간표 기준 도착 예정 시각이 지나면 종료 |
| 새로고침 복원 | 브라우저에 저장해 둔 진행 기록 |

![같은 상태를 다섯 곳에서 각자 덮어쓰고 있었다](/images/blogImg/alert-01-writers.png)

이 주체들이 서로 다른 시점에 비동기로 상태를 덮어쓰고 있었습니다. 그래서 개별 버그를 고치기 전에 원칙 네 가지부터 정했습니다.

1. 단계에는 순위가 있고, 앞으로만 간다.
2. 누가 최종 결정하는지 정한다.
3. 늦게 온 응답은 버린다.
4. 상태를 바꾸는 작업은 한 번에 하나만 한다.

---

# 🔍 2. 원칙 1: 단계는 앞으로만 간다

먼저 표시 단계에 순서를 매겼습니다.

![확인된 단계는 바닥이 되고, 아래로 내려가지 않는다](/images/blogImg/alert-02-forward-only.png)

새 관측이 들어오면 지금까지 확인된 단계를 바닥으로 두고, 그보다 낮은 단계의 관측은 화면에 반영하지 않습니다. 이미 "도착"을 확인했다면 그 뒤에 "곧 도착" 관측이 와도 "도착"을 유지합니다.

여기서 중요했던 건 "단계"와 "수치"를 구분하는 것이었습니다. 처음에는 모든 값을 앞으로만 가게 하려고 했지만, 그러면 안 되는 값이 있었습니다.

| 상황 | 처리 |
| --- | --- |
| 차량 정보 누락, 조회 실패 | 직전 진행 유지. 도착이나 탑승으로 보지 않음 |
| "곧 도착" 이후 남은 정류장 수가 늘거나 누락됨 | "곧 도착" 유지 |
| "도착" 이후 이전 단계 관측이 오거나 정보가 누락됨 | "도착" 유지 |
| "곧 도착" 전 남은 정류장 수 변화 | 새 관측을 그대로 반영 |

버스는 차량 교체나 데이터 공급자 차이 때문에 남은 정류장 수가 실제로 늘어나는 것처럼 보일 때가 있습니다. 그래서 단계 문구는 되돌리지 않되, 남은 정류장 수 같은 수치는 새 관측으로 갱신하도록 했습니다.

## 정보가 없다는 것은 도착했다는 뜻이 아니다

초기 구현에는 "일정 시간 동안 차량이 관측되지 않으면 이미 지나간 것으로 본다"는 규칙이 있었습니다. 그럴듯해 보였지만, 외부 API가 잠깐 장애를 일으키면 아직 오지도 않은 버스를 탑승 처리하는 문제가 생겼습니다.

이 규칙은 삭제했습니다. 지금은 같은 차량이 대상 정류장을 지난 것이 실제 위치로 확인될 때만 도착으로 판단합니다.

그 대가로, 장애가 길어지면 실제로는 지나갔는데도 "곧 도착"이 남아 있을 수 있습니다. 이 트레이드오프는 정책 문서에 명시해 두었습니다. 잘못된 확정보다는 늦은 확정이 낫다고 판단했습니다.

---

# 🔍 3. 원칙 2: 누가 최종 결정하는가

화면에서 관측한 정보와 서버 판정이 다르면 무엇을 믿어야 할까요? 서버를 기준으로 정했고, 화면 관측은 숫자 표시에만 사용합니다.

다만 서버 조회가 계속 실패하면 화면이 멈춰 버립니다. 그래서 대체 경로를 두었습니다.

| 서버 조회 결과 | 다음 판단 기준 |
| --- | --- |
| 성공 | 서버 판정 |
| 알림 없음(404) | 서버가 알림을 끝낸 것으로 보고 정리 |
| 일시적 실패 | 서버 판정 유지, 실패 횟수 누적 |
| 여러 번 연속 실패 | 화면 관측 기준으로 진행 |

이 판단 로직은 화면과 분리된 순수 함수로 만들었습니다. 덕분에 버스와 지하철이 같은 규칙을 공유하고, 화면 없이도 단위 테스트를 할 수 있게 됐습니다.

---

# 🔍 4. 원칙 3: 늦게 온 응답은 버린다

주기적 조회, 사용자 조작, 자동 종료가 겹치면 응답이 도착하는 순서가 요청한 순서와 달라집니다.

![먼저 보낸 요청이 나중에 도착할 수 있다](/images/blogImg/alert-03-stale-response.png)

이 문제는 두 가지 확인으로 막았습니다.

- **버전 비교**: 서버 응답에 담긴 revision을 비교해서, 이미 가진 것보다 오래된 응답은 적용하지 않습니다.
- **await 이후 재확인**: 응답을 기다리는 사이에 사용자가 로그아웃했거나 다른 알림으로 바꿨을 수 있습니다.

두 번째가 가장 놓치기 쉬운 부분이었습니다.

```ts
async function refresh(alertId: string) {
  const session = getSessionId()
  const snapshot = await fetchAlert(alertId)

  // 기다리는 동안 로그아웃했거나 다른 알림으로 바뀌었을 수 있다
  if (getSessionId() !== session || getActiveAlertId() !== alertId) return

  // 이미 더 최신 버전을 가지고 있다면 버린다
  const current = getCurrentAlert()
  if (current?.id === alertId && current.revision > snapshot.revision) return

  setCurrentAlert(snapshot)
}
```

`await` 다음 줄은 요청을 보낼 때와 다른 세상입니다. 이 기준을 세운 뒤로는 비동기 함수를 리뷰할 때 "기다리는 동안 무엇이 바뀔 수 있는가"를 먼저 확인하게 됐습니다.

같은 이유로, 서버 목록을 다시 받아오는 동안 사용자가 하차 정류장을 바꿨다면, 조회를 시작한 시점의 목록이 그 변경을 되돌리지 않도록 했습니다.

---

# 🔍 5. 원칙 4: 상태를 바꾸는 작업은 한 번에 하나만

등록, 변경, 자동 종료가 동시에 실행되면 결과를 예측할 수 없습니다. 그래서 화면을 이동해도 유지되는 앱 전역 작업 잠금을 두었습니다. 하나의 작업이 진행되는 동안에는 다른 작업이 시작되지 않습니다.

잠금에는 작업마다 고유 토큰을 발급하고, 자기 토큰일 때만 잠금을 풀 수 있게 했습니다. 작업 도중 계정이 바뀌어 새 작업이 시작됐다면, 이전 작업이 끝나면서 새 작업의 잠금까지 풀어 버리면 안 되기 때문입니다.

## 자동 종료 직전에 서버에 한 번 더 묻기

"시간표상 도착 시각이 지나면 알림을 종료한다"는 규칙에도 함정이 있었습니다. 사용자가 방금 열차를 바꿨는데 로컬에 이전 열차의 시각이 남아 있으면, 진행 중인 알림이 종료돼 버립니다.

![종료 직전, 로컬 값이 아니라 최신 상태로 다시 판단했다](/images/blogImg/alert-04-auto-end.png)

핵심은 두 가지입니다.

- 종료 판단은 로컬에 남은 값이 아니라, 방금 조회한 최신 상태로 다시 합니다.
- 해제 요청이 실패하면 로컬 상태를 지우지 않습니다. 서버에서는 살아 있는데 화면에서만 사라지는 상황이 가장 위험하기 때문입니다.

같은 알림에 종료 요청이 여러 번 들어오면 진행 중인 요청을 재사용해서 중복 호출도 막았습니다.

# 🔍 6. 동시 변경 충돌: 서버와 사용자가 동시에 고칠 때

지하철 실시간 추적 중에는 서버가 관측할 때마다 알림을 갱신합니다. 이때 사용자가 열차를 바꾸면 서버가 동시 변경 충돌(409)을 응답합니다.

해결 방법은 최신 상태를 다시 받아온 뒤 재시도하는 것입니다. 다만 재시도 횟수만 제한해서는 부족했습니다.

```ts
async function changeTrain(alertId: string, change: TrainChange, maxRetry = 2) {
  for (let attempt = 0; ; attempt++) {
    try {
      return await requestChange(alertId, change)
    } catch (error) {
      if (!isConflict(error) || attempt >= maxRetry) throw error

      const latest = await fetchAlert(alertId)
      // 그 사이 이미 탑승했다면 "열차 변경"은 더 이상 의미가 없다
      if (!canStillChange(latest, change)) throw error
    }
  }
}
```

충돌이 난 사이에 사용자가 이미 탑승했거나 해당 구간이 끝났다면, 재시도에 성공하는 것 자체가 잘못된 결과입니다. 몇 번 재시도할지보다, 재시도해도 되는 상황인지를 판단하는 것이 핵심이었습니다.

---

# 🔍 7. 알림 교체: 무엇을 먼저 할 것인가

알림은 한 번에 하나만 활성화됩니다. 지하철 알림이 진행 중인데 다른 알림을 새로 등록하면 기존 알림을 교체해야 합니다. 이때 순서가 문제였습니다.

| 순서 | 중간에 실패하면 | 선택한 경우 |
| --- | --- | --- |
| 기존 해제 → 새 등록 | 알림이 하나도 없음 | 사용자에게 교체 여부를 먼저 확인해 의도가 분명할 때 |
| 새 등록 → 기존 해제 | 알림이 두 개가 됨 | 새 알림이 더 중요할 때. 해제 실패는 부분 성공으로 안내 |

어느 쪽에도 완벽한 정답은 없었습니다. 그래서 상황별로 순서를 정하되, 한 가지 원칙은 지켰습니다. 성공한 것처럼 보이는 실패는 만들지 않는다는 것입니다.

새 알림은 설정됐지만 기존 알림 해제를 확인하지 못했다면, 교체 완료 메시지 대신 그 사실을 그대로 안내합니다.

---

# 🔍 8. 새로고침 복원: 저장된 기록은 새 관측이 아니다

새로고침하면 진행 단계가 처음으로 돌아가는 문제는 진행 기록을 브라우저에 저장해서 해결했습니다. 다만 저장된 값을 그대로 믿지는 않습니다.

| 검사 | 기준 |
| --- | --- |
| 대상 일치 | 노선, 차량, 승하차 단계, 목표 정류장이 모두 같을 때만 복원 |
| 유효기간 | 일정 시간이 지났거나 저장 시각이 미래면 버림 |
| 값 검증 | 손상되거나 형식이 맞지 않는 값은 버리고 새 관측으로 판단 |
| 의미 제한 | 복원한 값은 "예전에 본 값"일 뿐, 그것만으로 다음 단계로 넘어가지 않음 |

마지막 항목이 가장 중요했습니다. 복원은 화면을 이어서 보여주기 위한 것이지, 열차가 실제로 어디에 있는지 알려주는 근거가 아니기 때문입니다.

---

# 🔍 9. 검증: 버그마다 회귀 테스트 하나

이런 문제는 손으로 재현하기 어렵습니다. 그래서 가짜 타이머와 모듈 mock으로 시나리오를 테스트에 고정했습니다.

- 열차를 바꾸는 중에 자동 종료가 실행되는 경우
- 버스 차량을 교체하는 중에 이전 응답이 도착해 알림이 취소되는 경우
- 버스와 지하철 알림을 동시에 등록하는 경우
- 충돌 이후 이미 탑승한 상태라 재시도를 멈춰야 하는 경우

경쟁 조건을 하나 고칠 때마다 재현 시나리오를 회귀 테스트로 남겼습니다. 같은 문제가 다시 생기지 않게 하는 데는 이 방법이 가장 확실했습니다.

---

# 🔍 회고

## 배운 것

- 비동기 상태 버그는 하나씩 고치면 끝이 없습니다. 누가 상태를 바꾸는지, 무엇이 우선인지, 늦은 응답을 어떻게 처리할지 규칙을 먼저 세우자 개별 버그들이 같은 방법으로 정리됐습니다.
- "앞으로만 간다"는 규칙도 모든 값에 적용하면 안 됩니다. 단계와 수치를 구분해야 했습니다.
- `await` 다음 줄은 다른 세상입니다. 기다리는 동안 무엇이 바뀌었을 수 있는지 항상 다시 확인해야 합니다.
- 판단 로직을 화면과 분리하자 버스와 지하철이 같은 규칙을 공유했고, 테스트도 쉬워졌습니다.

## 남은 한계

- 데이터 공급자의 장애가 길어지면 실제로는 지나간 차량이 "곧 도착"으로 남을 수 있습니다. 의도한 트레이드오프지만, 사용자에게 더 나은 안내 방법은 계속 고민하고 있습니다.
- 단위 테스트로는 실제 기기, 지도 SDK, 푸시 수신까지 보장하지 못합니다. 그 부분은 실기기 검증 범위로 따로 관리합니다.
